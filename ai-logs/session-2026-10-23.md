 * No floats anywhere: ETH has 18 decimals, which a JS number cannot represent.

/** The API's amount grammar: digits with an optional dot and more digits, no leading zeros. */
const AMOUNT_RE = /^(0|[1-9]\d*)(?:\.(\d+))?$/;

export type ParseReason = "empty" | "format" | "too_many_decimals";
export type ParseResult = { ok: true; units: bigint } | { ok: false; reason: ParseReason };

/** Trims and turns a comma decimal separator (EU keyboards) into a dot. */
export function normalizeInput(input: string): string {
  return input.trim().replace(",", ".");
}

/** Parses user input into units, enforcing the API grammar and the asset's decimals. */
export function parseAmount(input: string, decimals: number): ParseResult {
  const text = normalizeInput(input);
  if (text === "") return { ok: false, reason: "empty" };
  const match = AMOUNT_RE.exec(text);
  if (!match) return { ok: false, reason: "format" };
  const whole = match[1];
  const fraction = match[2] ?? "";
  if (fraction.length > decimals) return { ok: false, reason: "too_many_decimals" };
  return { ok: true, units: BigInt(whole + fraction.padEnd(decimals, "0")) };
}

  const [now, setNow] = useState(() => Date.now());

    return () => clearInterval(timer);

## assistant · 2026-10-23T20:09:18.212Z

Three approaches, each one a different answer to "who owns the number on screen". Facts that constrain all of them: the snapshot can be up to 15 s stale, `POST /v1/claims` moves the amount out of `available` immediately on the server, a failed claim puts it back ~20 s later, and `available` is re-checked live on every claim.

## A. Optimistic local update

**User sees:** the moment Confirm succeeds, `available` drops by the claimed amount and `claiming` rises. When the next snapshot arrives it replaces the local numbers.

**Complaint 1 (claimed twice):** solved; the number changes instantly, so there is no "nothing happened" moment.
**Complaint 2 (jumped back):** this approach *is* that complaint. Two ways it happens: (a) a snapshot with an older `asOf` than the claim arrives via the 15 s poll and overwrites the optimistic number upwards, then the next one drops it again; (b) the claim fails within ~20 s and the amount legitimately returns. In both cases the user watches a balance move in two directions within half a minute.

**Failure modes:** unknown-outcome claims (504/timeout) are the hard part. Either you apply the optimistic subtraction for something that may not exist, or you don't and you're back to complaint 1 for exactly the riskiest case. You can patch (a) by ignoring snapshots whose `asOf` is older than the claim's `createdAt`, but then you are already building approach C's reconciliation logic.

## B. Server truth only, plus explicit pending UI

**User sees:** the balance numbers never change except when a new snapshot arrives. **Complaint 1:** mitigated, not solved. The number still looks unchanged for up to 15 s; what stops the second claim is the disabled button and the banner. **Failure modes:** polling must keep going while something is pending (we already poll every 15 s; could tighten to 5 s while a claim is in flight). Weakness: honesty costs feedback; the headline looks wrong for a while and the user has to trust the banner.

**Complaint 1:** solved, and by construction rather than by messaging: the amount the user can type is already reduced, so even if they ignore every banner, the server would reject an over-claim and the form won't offer it. **Complaint 2:** solved for the headline (it only moves when the server says so). The *effective* figure moves once, monotonically, and is labelled as a derived number, so it does not read as "my balance jumped".

**Failure modes:** clock skew between server `asOf` and the claim's `createdAt` is the only subtle one, and both timestamps are server-generated, so the comparison is safe. An unknown-outcome attempt counts as in flight (reducing `effective`) until resolved by resending with the same idempotency key; worst case the user is offered slightly less than they could claim for a few seconds, which is the conservative direction. If the user clears their browser storage the overlay is lost, but the server numbers are still right.

**Cost in our code:** medium. Same claims store as B, plus `effectiveAvailable(asset, snapshot, inFlight)` with the `asOf` comparison (pure, unit-testable alongside `money.ts`), an extra line in `AssetCard`, and the claim form reading `effective` instead of `available`. ~120 lines. - Whichever you choose, the unknown-outcome case should count as in flight: it is the one scenario where double-claiming actually costs money, and it's exactly where idempotency keys pay for themselves.
